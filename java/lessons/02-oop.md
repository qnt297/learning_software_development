## この章の目標

- オブジェクトを **状態（state）** と **振る舞い（behavior）** で説明できる
- クラスとインスタンスの違いを説明できる
- クラスとインターフェイスの違い・使い分けを判断できる
- カプセル化（フィールドを隠す）の意図を理解する
- 継承とインターフェイスの使い分けを知る
- ポリモーフィズムで「差し替え可能な設計」の入口に立つ
- アノテーション（`@Override` など）の役割を説明できる

## なぜ大事か

現実のソフトウェアは「ユーザー」「注文」「在庫」など、複数の概念が協調して動きます。  
OOP は、それらを **責務のあるオブジェクト** としてモデル化する考え方です。

手続きだけを並べたコードでも動きますが、規模が大きくなると「どのデータにどの処理が属するか」が曖昧になり、修正のたびに無関係な箇所まで触れがちです。OOP は、その地図をコード構造そのものに埋め込みます。

## 学習ポイント

### 1. オブジェクトは「状態」と「振る舞い」の束

Oracle の Java チュートリアル（[What Is an Object?](https://docs.oracle.com/javase/tutorial/java/concepts/object.html)）では、現実世界のモノもソフトウェアのオブジェクトも、次の2つで捉えられる、と説明されています。

| 概念 | 英語 | ソフトウェアでの対応 | 例（本） |
|------|------|----------------------|----------|
| **状態** | state | フィールド（変数）に保持する情報 | タイトル、著者、貸出中か |
| **振る舞い** | behavior | メソッドとして公開する操作 | 借りる、返す、表示する |

実世界の例（同チュートリアルの自転車イメージ）:

- 状態: 現在のギア、ペダル回転、速度
- 振る舞い: ギアを変える、ブレーキをかける

これをコードに落とすと:

```java
public class Bicycle {
    // ----- 状態 (state) -----
    private int gear;
    private int speed;

    // ----- 振る舞い (behavior) -----
    public void changeGear(int newGear) {
        if (newGear < 1 || newGear > 6) {
            throw new IllegalArgumentException("gear out of range");
        }
        this.gear = newGear;
    }

    public void applyBrake(int decrement) {
        speed = Math.max(0, speed - decrement);
    }
}
```

重要な含意（チュートリアルと同趣旨）:

1. **メソッドが状態を操作する** … 外からフィールドを直接いじらせず、振る舞い経由にする（これがカプセル化につながる）
2. **オブジェクト同士はメソッド呼び出しで会話する** … データの投げ合いではなく、メッセージ（操作の依頼）
3. **状態を自分で守る** … 例: ギアが6段しかないなら、`changeGear(99)` を拒否できる

「データ構造＋別ファイルの手続き」ではなく、**関連する状態と振る舞いを同じオブジェクトにまとめる** のが OOP の出発点です。

参考（Oracle）:

- [Object-Oriented Programming Concepts](https://docs.oracle.com/javase/tutorial/java/concepts/)
- [What Is an Object?](https://docs.oracle.com/javase/tutorial/java/concepts/object.html)
- [What Is a Class?](https://docs.oracle.com/javase/tutorial/java/concepts/class.html)
- [What Is an Interface?](https://docs.oracle.com/javase/tutorial/java/concepts/interface.html)

### 2. クラスとインスタンス

- **クラス**: 状態と振る舞いの設計図（blueprint）。Oracle の表現では「オブジェクトを作るための原型」
- **インスタンス**: 設計図から作られた実体。同じクラスでも **状態は別々**、振る舞いの形は共有

```java
Book book1 = new Book("Clean Code", "Robert C. Martin");
Book book2 = new Book("Effective Java", "Joshua Bloch");
// book1 を借りても book2 の貸出状態は変わらない＝状態はインスタンスごと
```

#### もう少し詳しく

- `new` のたびに、ヒープ上に別オブジェクトが作られる
- 変数 `book1` が持つのはオブジェクトそのものではなく、参照（住所のようなもの）
- クラスに `static` な要素を置くと「全インスタンスで共有」になる。便利だが、共有状態はテストと並行処理を難しくしやすい

#### 設計での使い方

- 「名詞」をクラス候補にする（Book, Order, Customer）
- 候補ごとに「状態は何か？振る舞いは何か？」を書き出す（Oracle 流の観察法）
- 「動詞だけ」をクラスにしない（`DoSomethingManager` のような曖昧名は責務が拡散しやすい）
- 1つのクラスが抱え込む知識が多すぎないか、常に疑う（後の単一責任へ）

### 3. カプセル化

フィールドを `private` にし、公開メソッド経由で操作します。  
状態を隠し、振る舞いだけを外に出すことで、不正な状態遷移を防ぎます（前節のギア例と同じ発想です）。

```java
public class BankAccount {
    private int balance;

    public void deposit(int amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("amount must be positive");
        }
        balance += amount;
    }

    public int getBalance() {
        return balance;
    }
}
```

#### 目的は「隠すこと」ではなく「守れない状態を作らせないこと」

カプセル化の本質は、次の **不変条件（invariant）** をクラス自身が守ることです。

- 残高は負にならない
- 借り済みの本を二重に貸せない
- 必須項目が空の注文を確定できない

getter/setter を機械的に生やすだけではカプセル化ではありません。特に、

```java
// 悪い例: 外から自由に壊せる
public int balance;
```

や、チェックなしの `setBalance(-100)` は、クラスが責任を放棄している状態です。

#### 実務での効果

- 呼び出し側は「使い方（メソッド）」だけ知ればよい
- 内部表現（配列→List、int→Money 型など）を後から変えやすい
- バグの調査範囲が「そのクラスのメソッド」に寄りやすい

### 4. 継承（is-a）

共通の性質を親クラスにまとめ、子クラスで差分を表現します。

```java
public abstract class Shape {
    public abstract double area();
}

public class Circle extends Shape { /* ... */ }
```

「円 **は** 図形である」のように、意味的に is-a が成立する場合の道具です。

#### メリット

- 共通処理の重複を減らせる
- 親の型でまとめて扱える（ポリモーフィズムの土台）

#### デメリット・注意点

- 親を変えると子全体に影響する（結合が強い）
- 深く長い継承ツリーは理解コストが高い
- 「ちょっと共通だから継承」は、後で is-a が破綻しやすい（例: Square extends Rectangle 問題）

#### 実務での指針

- 継承は **浅い・安定した階層** に限定する
- 「コード再利用のためだけ」の継承は避け、委譲（持っているオブジェクトに任せる）を優先する
- `abstract` で「未完成の設計図」を明示し、誤って親を直接 `new` できないようにする

### 5. インターフェイス（can-do）と、クラスとの使い分け

Oracle の説明では、インターフェイスは **クラスと外界との契約（contract）** です。  
実装クラスは、その契約で約束した振る舞いを提供することを誓います（[What Is an Interface?](https://docs.oracle.com/javase/tutorial/java/concepts/interface.html)）。

```java
public interface Payment {
    String methodName();
    int pay(int amount);
}
```

`CashPayment` も `CardPayment` も `Payment` を実装でき、呼び出し側は具体クラスを知らなくてよい場合があります。

#### クラスとインターフェイスの違い

| 観点 | クラス | インターフェイス |
|------|--------|------------------|
| 本質 | 状態＋振る舞いの具体的な設計図 | 振る舞いの契約（何ができるか） |
| インスタンス化 | `new` できる（抽象クラス除く） | 直接 `new` できない |
| 状態（フィールド） | インスタンス状態を持てる | 定数以外のインスタンスフィールドは持たない（Java の基本） |
| 多重 | クラス継承は基本1つ（`extends`） | 複数実装できる（`implements`） |
| 目的 | もの／概念を表す | 能力・役割・差し替え点を表す |

※ Java 8 以降、インターフェイスに `default` / `static` メソッドを書けるようになりましたが、それでも「契約が本体」という位置づけは変わりません。

#### どういうときにクラスを使うか

- 状態を持ち、その状態を守る振る舞いが必要（`Book`, `Order`, `BankAccount`）
- 業務上の「もの」や「出来事」をモデル化したい
- 実装を1つに固定してよい（差し替え前提がない）

#### どういうときにインターフェイスを使うか

- **実装を差し替えたい**（支払い方法、保存先、通知チャネル）
- **テストで偽物（モック）に置き換えたい**
- 複数の無関係なクラスに、同じ能力を持たせたい（`Comparable`, `AutoCloseable`）
- 呼び出し側を具象クラスに依存させたくない（09 章の依存性逆転）

#### 継承（クラス）とインターフェイス、どちらを先に考えるか

| 問い | 向き |
|------|------|
| 「A は B の一種か？」が強い | クラス継承（ただし浅く） |
| 「A は ○○できる」が本質 | インターフェイス |
| コードを共有したいだけ | 継承より **委譲**（持つ・任せる） |
| 両方必要 | 抽象クラスで骨格＋インターフェイスで役割、もあり |

**継承よりインターフェイス＋コンポジション** を優先する、が現代的なデフォルト方針です。継承は「本当に種類の階層がある」ときに使います。

### 6. ポリモーフィズム

同じメソッド呼び出しでも、実行時の実体の型によって振る舞いが変わることです。

```java
Payment payment = new CardPayment("4242");
payment.pay(1000); // CardPayment の実装が呼ばれる

payment = new CashPayment();
payment.pay(1000); // CashPayment の実装が呼ばれる
```

呼び出し側のコードは `payment.pay(...)` のままです。ここに `if (type == CARD)` のような分岐を増やさずに済みます。

#### なぜ重要か

- 新支払い手段を追加しても、既存の checkout 処理を大きく書き換えなくてよい（開放閉鎖原則の入口）
- 「使う側」と「作る側」の責任が分かれる

#### 注意点

- 型を見てまた `instanceof` で分岐し始めると、ポリモーフィズムの恩恵が消える
- 振る舞いの差は、できるだけ各実装クラス側に閉じ込める

### 7. アノテーション

アノテーションは、コードに付与する **メタデータ（付加情報）** です。  
実行そのものの計算ロジックというより、「このメソッドは親のオーバーライド」「この API は非推奨」「これはテスト」といった意図を、コンパイラやフレームワークに伝えます。

```java
@Override
public double area() {
    return Math.PI * radius * radius;
}
```

#### なぜ OOP と一緒に学ぶか

- `@Override` … 継承／インターフェイス実装のミスをコンパイル時に防げる
- `@FunctionalInterface` … ラムダ用の「メソッドが1つ」の契約を明示（06 章とも接続）
- フレームワーク（Spring の `@Service`、JUnit の `@Test` など）は、アノテーションで「役割」を宣言するスタイルが主流

OOP で構造を作り、アノテーションで **道具（コンパイラ／実行基盤）への合図** を添える、という関係です。

#### よく使う組み込みアノテーション

| アノテーション | 意味 |
|----------------|------|
| `@Override` | 親クラス／インターフェイスのメソッドを上書きしている宣言。署名ミスを検出 |
| `@Deprecated` | 非推奨。呼び出し側に警告を出す（代替手段を Javadoc や `since` / `forRemoval` で示す） |
| `@SuppressWarnings` | 特定警告を抑制。安易に広い範囲へ付けない |
| `@FunctionalInterface` | 関数型インターフェイスであることの明示 |
| `@SafeVarargs` | 可変長引数とジェネリクス併用時の警告抑制（上級） |

#### カスタムアノテーション（入口）

自分でも定義できます。

```java
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Retention(RetentionPolicy.RUNTIME) // 実行時にも残す
@Target(ElementType.METHOD)         // メソッドにだけ付与可
public @interface Audited {
    String value() default "";
}
```

| メタアノテーション | 役割 |
|--------------------|------|
| `@Target` | どこに付けられるか（型・メソッド・フィールドなど） |
| `@Retention` | いつまで残るか（ソースのみ / クラスファイル / 実行時） |

実行時に読む（リフレクション）場合は `RUNTIME` が必要です。コンパイルチェックだけなら `SOURCE` や `CLASS` で足りることもあります。

#### 実務での付き合い方

- **まず標準の `@Override` を習慣にする**（IDE が付けてくれることも多い）
- `@SuppressWarnings("unchecked")` は理由コメント付きで最小範囲に
- フレームワークのアノテーションは「魔法」ではなく、起動時／コンパイル時に誰かが解釈している、と理解する
- 詳細な DI アノテーションは Spring 等の学習時に深掘りでよい（この章では概念と `@Override` までで十分）

JUnit の `@Test` は [08. ユニットテスト入門](08-testing.md)、GoF パターンとの設計語彙は [09. 設計の基礎](09-design.md) で続きます。

## 学習ポイントの関係図

```text
状態 + 振る舞い … オブジェクトの正体（Oracle の基本モデル）
        ↓
クラス/インスタンス … 設計図と実体
        ↓
カプセル化 … 状態を守り、振る舞いだけ公開
        ↓
クラス継承 / インターフェイス … 種類の共有 vs 能力の契約
        ↓
ポリモーフィズム … 差し替え可能な協調
        ↓
アノテーション … 意図をコンパイラ／基盤へ伝える
```
