## この章の目標

- SOLID の入口（特に S / O / D）を具体例で理解する
- 疎結合・密結合、DRY、再利用と車輪の再発明など、多角的な設計観点を持つ
- GoF デザインパターンの分類と代表例を説明できる
- Strategy / Factory Method / Decorator / Repository の考え方を知る
- GoF 全23パターンを参考カタログとして概観できる
- 「動くコード」から「変えやすいコード」へ意識を移す

## なぜ大事か

要件は必ず変わります。設計が貧弱だと、1つの変更が広範囲に波及します。  
良い設計は、変更の影響範囲を局所化するための技術です。原則は暗記対象ではなく、**トレードオフを語るための語彙** です。

GoF パターンは、その語彙の古典的なカタログです。「この問題、前にも見た」をチームで共有するための地図になります。

## 学習ポイント

### 1. SOLID（入口）

| 原則 | 一言 |
|------|------|
| S: 単一責任 | クラスの理由は一つ |
| O: 開放閉鎖 | 拡張に開き、修正に閉じる |
| L: リスコフ | サブタイプは契約を破らない |
| I: インタフェース分離 | 太った IF を避ける |
| D: 依存性逆転 | 具象ではなく抽象に依存 |

まずは **単一責任** と **依存性逆転** からで十分です。

### 2. 疎結合と密結合

結合度は「あるモジュールを変えたとき、他がどれだけ巻き込まれるか」です。

| | 密結合 | 疎結合 |
|--|--------|--------|
| 状態 | 具象クラス・共有可変状態・巨大な神クラスに依存 | インターフェイス・明確な入力出力・小さな責務 |
| 変更時 | 連鎖修正が起きやすい | 影響が局所に収まりやすい |
| テスト | モック困難、起動が重い | 単体で差し替えやすい |

```java
// 密結合寄り: 具象にべったり
class CheckoutService {
    private final WeightShipping shipping = new WeightShipping(200);
}

// 疎結合寄り: 抽象に依存（コンストラクタ注入）
class CheckoutService {
    private final ShippingFeePolicy shipping;

    CheckoutService(ShippingFeePolicy shipping) {
        this.shipping = shipping;
    }
}
```

完全な「結合ゼロ」は不可能です。目指すのは、**変わる可能性の高い部分との結合を薄くする** ことです。  
サンプルの Strategy / Repository は、まさに疎結合のためのパターンです。

### 3. DRY（Don't Repeat Yourself）

「同じ知識を、複数箇所に重複して書かない」原則です。

- 悪い重複: 同じ割引計算式が画面・API・バッチにコピペされている → 片方だけ直して不整合
- 良い共通化: その計算を `DiscountPolicy` やドメインサービスに集約する

#### DRY の誤解（やりすぎ注意）

- **見た目が似ているだけ** のコードを無理に共通化すると、無関係な事情が1クラスに混ざる
- 共通化の結果、引数だらけの `Util` 神クラスになるのは失敗パターン
- 「今は似ているが、変化の理由が違う」なら、あえて重複を残す方が保守しやすいことがある（**過剰な DRY は密結合を生む**）

指針: **重複しているのはコードか、それとも「知識・ルール」か？** ルールの重複を解消する。

### 4. 車輪の再発明（と、その逆）

**車輪の再発明** とは、既に十分よいライブラリや言語機能があるのに、同等のものを自作してしまうことです。

| やりがち | まず検討するもの |
|----------|------------------|
| 自作 JSON パーサ | Jackson / Gson など |
| 自作日付計算の嵐 | `java.time` |
| 自作 DI コンテナ | Spring 等（必要なら） |
| 自作テストランナー | JUnit |

再発明のコストは、実装だけではありません。**バグ修正・セキュリティ・ドキュメント・後任への説明** がずっと付いて回ります。

#### それでも自作してよいとき

- 学習目的（この教材の簡易 Assert など）で、本番投入しない
- 要件が特殊で、既存ライブラリが重い／合わない
- 依存を増やせない制約（組込み、セキュア環境など）がある
- コアコンピタンスそのもので、差別化になる

#### 逆の失敗: 依存の足しすぎ

ライブラリを足すたびに、版冲突・脆弱性対応・学習コストが増えます。  
「再発明するな」と「何でも依存追加」は両立しません。**標準ライブラリ → 実績ある小依存 → 自作** の順で検討するのが実務的です。

### 5. その他の多角的な観点

| 観点 | 問い |
|------|------|
| **YAGNI** | 今必要ない拡張ポイントを、想像だけで作り込んでいないか |
| **KISS** | もっと単純な解がないか。パターンのためのパターンになっていないか |
| **可読性** | 3ヶ月後の自分が一読で意図を追えるか |
| **テスタビリティ** | ユニットテストが書きにくくないか（書きにくさは設計の匂い） |
| **変更容易性** | 仕様変更のとき、直す場所は一箇所に寄るか |
| **一貫性** | チーム内の命名・層分割・例外方針と揃っているか |
| **パフォーマンス** | 計測前に複雑化していないか。まず正しく、次に速く |
| **セキュリティ** | 境界で入力検証しているか。秘密情報をログ／例外に出していないか |

これらはしばしば衝突します（例: 抽象化で疎結合にする ↔ YAGNI／KISS）。  
設計レビューでは「どれを優先するか」をチームで合意することが重要です。

### 6. GoF デザインパターンとは

**GoF（Gang of Four）** は、書籍 *Design Patterns: Elements of Reusable Object-Oriented Software*（1994）の著者4名を指します。  
そこで整理された **23 のデザインパターン** は、OOP における「再利用可能な設計の型紙」の古典です。

パターンは「コピペ用テンプレート」ではなく、

- どんな力（変更・拡張・複雑さ）に対処するか
- どんなトレードオフがあるか

を共有するための **名前付きの設計判断** です。

#### 3つの分類

| 分類 | 目的 | 代表例 |
|------|------|--------|
| **生成（Creational）** | オブジェクトの作り方を柔軟にする | Factory Method, Abstract Factory, Builder, Singleton, Prototype |
| **構造（Structural）** | クラス／オブジェクトの組み立て方 | Adapter, Decorator, Facade, Proxy, Composite, Bridge, Flyweight |
| **振る舞い（Behavioral）** | 責務の分担と相互作用 | Strategy, Observer, Template Method, Command, Iterator, State, … |

#### まず押さえる代表パターン（紹介）

**生成**

| パターン | 一言 | 使うとき |
|----------|------|----------|
| **Factory Method** | 生成処理をサブクラス／専用メソッドに任せる | `new` の分岐が散らばり、生成ロジックを一箇所に集めたい |
| **Builder** | 複雑な構築を段階的に行う | 引数が多すぎる・必須／任意が混在するオブジェクト |
| **Singleton** | インスタンスを1つに制限 | 本当に全体で1つ必要なときだけ（乱用注意・テストしづらい） |

**構造**

| パターン | 一言 | 使うとき |
|----------|------|----------|
| **Adapter** | 既存のインタフェースを別のインタフェースに合わせる | 外部ライブラリの API を自システムの契約に合わせる |
| **Decorator** | 責務をラップして動的に足す | 継承爆発を避けつつ、機能を組み合わせたい |
| **Facade** | 複雑な子系统へ単純な入口を用意 | 呼び出し側に内部詳細を見せたくない |
| **Proxy** | 代理を挟んでアクセスを制御 | 遅延生成、権限、キャッシュ、リモート呼び出しなど |

**振る舞い**

| パターン | 一言 | 使うとき |
|----------|------|----------|
| **Strategy** | アルゴリズムを差し替え可能にする | if/switch で計算方針が増え続ける |
| **Observer** | 状態変化を購読者へ通知 | イベント駆動、UI 更新、ドメインイベント |
| **Template Method** | 処理の骨格を親が決め、差分を子が埋める | 手順は同じで一部だけ変えたい（継承前提） |
| **Command** | 要求をオブジェクトとして表現 | Undo、キューイング、操作のログ |
| **Iterator** | 集合の辿り方を隠す | Java の `Iterator` / 拡張 for が典型 |

この教材のサンプルでは、特に重要な次を具体コードで扱います。

- **Strategy**（振る舞い）… 送料計算の差し替え
- **Factory Method**（生成）… 通知チャネルの生成
- **Decorator**（構造）… メッセージ加工の重ね合わせ

以下は **参考カタログ（全23）** です。すべて暗記する必要はありません。名前と「どんな力に効くか」を地図として持っておくのが目的です。

#### 参考: GoF 全23パターン

##### 生成（Creational）— 5

| # | パターン | 概要（参考） | 現代 Java での接点 |
|---|----------|--------------|-------------------|
| 1 | **Abstract Factory** | 関連する製品群（例: Button+Checkbox の Look&Feel）を、具象を知らずにまとめて生成する | UI キット、環境ごとの実装セット |
| 2 | **Builder** | 複雑なオブジェクトをステップで構築。必須／任意・順序を制御しやすい | Lombok `@Builder`、レコード構築、テストデータ用意 |
| 3 | **Factory Method** | 生成をメソッド／サブクラスに委譲し、呼び出し側を具象から切り離す | 本教材サンプル、JDK の factory メソッド群 |
| 4 | **Prototype** | 既存インスタンスを複製して新しいオブジェクトを得る | `Cloneable`（扱い注意）、コピーコンストラクタ、ディープコピー設計 |
| 5 | **Singleton** | 実行過程でインスタンスを1つに制限し、大域的なアクセス点を提供 | enum singleton、DI コンテナのスコープ。**乱用注意** |

##### 構造（Structural）— 7

| # | パターン | 概要（参考） | 現代 Java での接点 |
|---|----------|--------------|-------------------|
| 6 | **Adapter** | 互換性のないインタフェースを橋渡しして使えるようにする | レガシー API ラップ、ライブラリ差分の吸収 |
| 7 | **Bridge** | 抽象と実装を分離し、それぞれ独立に拡張できるようにする | ドライバ／プラットフォーム差分の分離 |
| 8 | **Composite** | 木構造で「葉」と「節」を同じインタフェースで扱う | ファイルシステム、UI コンポーネントツリー、組織図 |
| 9 | **Decorator** | 同一インタフェースでラップし、責務を動的に追加する | 本教材サンプル、`java.io` のストリームラップ、Servlet Filter 的発想 |
| 10 | **Facade** | 複雑なサブシステムへ、単純な窓口を提供する | アプリの Application Service、SDK の高水準 API |
| 11 | **Flyweight** | 内的状態を共有し、大量オブジェクトのメモリを節約する | 文字のグリフ共有、キャッシュされた不変値オブジェクト |
| 12 | **Proxy** | 代理オブジェクト経由でアクセス制御・遅延・遠隔などを付加する | 仮想 Proxy、`java.lang.reflect.Proxy`、Spring AOP の仕組みに近い発想 |

##### 振る舞い（Behavioral）— 11

| # | パターン | 概要（参考） | 現代 Java での接点 |
|---|----------|--------------|-------------------|
| 13 | **Chain of Responsibility** | 要求をハンドラの鎖に渡し、処理できるオブジェクトが引き受ける | サーブレット Filter チェイン、ログのハンドラ連鎖 |
| 14 | **Command** | 操作をオブジェクト化し、キュー・履歴・Undo を可能にする | メニュー操作、ジョブキュー、イベントソーシングの入口 |
| 15 | **Interpreter** | 簡易言語の文法をオブジェクト構造で表現し評価する | 小さな DSL、正規表現エンジンの思想（大規模では専用パーサへ） |
| 16 | **Iterator** | 集合の内部構造を隠したまま要素を順に辿る | `Iterator`、拡張 for、Stream の源泉 |
| 17 | **Mediator** | オブジェクト同士の直接参照を減らし、仲介者経由で協調させる | チャットルーム、UI のフォーム連携、メッセージブローカー的発想 |
| 18 | **Memento** | カプセル化を破らずに内部状態のスナップショットを保存・復元する | Undo、下書き保存 |
| 19 | **Observer** | 状態変化を購読者へ通知する（発行／購読） | イベントリスナ、Reactive Streams、ドメインイベント |
| 20 | **State** | 状態ごとに振る舞いをクラス分割し、状態遷移を明確にする | 注文ステータス、コネクション状態機械 |
| 21 | **Strategy** | アルゴリズムを差し替え可能なオブジェクトとして分離する | 本教材サンプル、Comparator、割引／送料ポリシー |
| 22 | **Template Method** | 処理の骨格を親が固定し、差分ステップだけを子が実装する | 抽象クラスのフックメソッド、テストの fixture 骨格 |
| 23 | **Visitor** | データ構造側を変えずに、新しい操作を外部から追加しやすくする | 構文木の走査、コンパイラ／静的解析。双方向依存に注意 |

##### 学習の優先度（参考）

| 優先 | パターン |
|------|----------|
| 高（まず実務で名前が出る） | Strategy, Factory Method, Decorator, Adapter, Observer, Facade, Builder, Template Method, Singleton（是非を含めて） |
| 中 | Proxy, Command, State, Composite, Abstract Factory, Chain of Responsibility |
| 低〜必要になったら | Bridge, Flyweight, Prototype, Mediator, Memento, Interpreter, Visitor |

#### GoF と現代 Java

- **Iterator / Observer / Factory** の考え方は、標準 API やフレームワークに溶け込み済み
- **Singleton** は DI コンテナ（Spring のデフォルトスコープ等）に任せることが多い
- **Template Method** より、Strategy や関数型（ラムダ渡し）の方が好みやすい場面もある
- パターン名を知っていると、コードレビューや設計議論が速くなる
- 詳細実装が必要になったら、上表の「現代 Java での接点」から逆引きすると学びやすい

#### アンチパターン: パターンのためのパターン

- 問題が小さいのに全パターンを適用して複雑化する
- 名前だけ借りて、意図と構造がずれている
- 「Singleton にすれば簡単」でグローバル状態を増やす

**原則（SOLID / 疎結合 / YAGNI）を先に**、パターンはその具体化手段、という順番が安全です。

### 7. Strategy パターン（GoF・振る舞い）

アルゴリズムを差し替え可能にします。

```java
public interface ShippingFeePolicy {
    int calculate(int weightGram);
}
```

if 分岐で送料種別を増やし続ける代わりに、実装クラスを追加します（開放閉鎖の実践）。

### 8. Factory Method パターン（GoF・生成）

「どれを `new` するか」を呼び出し側から切り離します。

```java
Notifier notifier = NotifierFactory.create("email");
notifier.send("hello");
```

呼び出し側は具象クラス名を知らなくてよく、生成ルールの変更が Factory に閉じます。

### 9. Decorator パターン（GoF・構造）

同じインターフェイスでラップし、責務を重ねます。

```java
Notifier notifier = new EmailNotifier();
notifier = new PrefixDecorator(notifier, "[INFO] ");
notifier = new UpperCaseDecorator(notifier);
notifier.send("hello");
```

継承で `EmailWithPrefixAndUpperCaseNotifier` のように組み合わせ爆発させる代わりに、ラップの順序で機能を足せます。

### 10. Repository の考え方

ドメインは「保存の詳細」を知りません。抽象に依存します。  
（GoF そのものではありませんが、エンタープライズで頻出のパターンで、疎結合の実践です。）

```java
public interface TaskRepository {
    void save(Task task);
    List<Task> findAll();
}
```

実装（メモリ / ファイル / DB）は差し替え可能です。これが疎結合とテスタビリティに直結します。

### 11. 設計レビューの問い

- このクラスは何の専門家か？（単一責任）
- 変更理由は何種類あるか？
- どこと密結合しているか？ それは意図的か？
- 同じルールが他にもコピペされていないか？（DRY）
- 自前実装は、既存の標準／ライブラリで足りないか？（車輪の再発明）
- 今の悩みは、GoF のどの力（生成／構造／振る舞い）に近いか？
- テストするためにモックが必要すぎないか？
- 今作っている拡張は、本当に今必要か？（YAGNI）
