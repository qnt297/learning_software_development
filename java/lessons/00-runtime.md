## この章の目標

- JDK / JRE / JVM の違いを説明できる
- `javac` と `java` で何が起きているか追える
- なぜ `main` から実行が始まるかを説明できる
- スタック・ヒープ・スコープの関係を、変数の寿命として説明できる
- GC と「キャッシュ」という言葉が指す層の違いを区別できる

## なぜ大事か

文法だけ覚えても、「なぜそこで落ちたか」「なぜメモリを食うか」は見えません。  
実行環境の地図があると、エラーメッセージ・性能・スコープのバグを、推測ではなく仕組みで説明できるようになります。

## 学習ポイント

### 1. JDK / JRE / JVM

| 名前 | 役割 |
|------|------|
| **JVM** | Java Virtual Machine。バイトコードを実行する仮想マシン |
| **JRE** | JVM + 標準ライブラリ。実行するための一式 |
| **JDK** | JRE + コンパイラ（`javac`）など開発ツール。学習・開発では JDK を入れる |

現代の配布は JDK にまとまっていることが多く、「実行だけなら JRE」という区別は薄れつつあります。  
研修では **JDK 17 以上** を入れておけば十分です。

Java の売りは **Write Once, Run Anywhere** です。ソースを一度バイトコードにし、各 OS 用の JVM が実行します。ネイティブの `.exe` を OS ごとに作り直す必要が原則ありません。

### 2. ソースから実行まで

```text
HelloWorld.java     javac        HelloWorld.class      java
  (ソース)      ─────────►     (バイトコード)     ─────────►  実行
```

1. 人が書いた `.java` を `javac` がコンパイルする
2. 成果物は `.class`（JVM 向けの中間コード）
3. `java HelloWorld` で JVM が起動し、クラスを読み、実行する

JVM 内部では、最初は解釈実行、よく実行される箇所は **JIT（Just-In-Time）コンパイラ** がマシン語に直し、以後は速くなります。

```bash
javac HelloWorld.java
java HelloWorld
```

`java HelloWorld` の引数は **クラス名** です（ファイル名の `.class` は付けない）。パッケージがある場合は FQCN（例: `com.example.App`）です。

### 3. なぜ main から始まるのか

OS が直接 Java のメソッドを呼ぶわけではありません。流れは次です。

```text
java コマンド
  → JVM 起動
    → 指定クラスをロード
      → 規約どおりの main を探す
        → main を呼び出す
```

JVM が探す署名はこれです。

```java
public static void main(String[] args)
```

| 要素 | 理由 |
|------|------|
| `public` | JVM がクラスの外から呼べるようにする |
| `static` | インスタンスを `new` する前でも呼べる（起動時点ではまだオブジェクトが無い） |
| `void` | 戻り値で OS に成功／失敗を返さない（終了コードは `System.exit` 等） |
| `String[] args` | コマンドライン引数を受け取る口 |

これが **エントリポイント（プログラムの入口）** です。  
C 言語の `main` と同じ役割で、「ここから人間のコードが始まる」という JVM との契約です。

`main` が無い、名前が違う、`static` が無い、と起動できません。  
Web アプリ（Spring Boot など）も、内部では起動クラスの `main` からコンテナが立ち上がります。

### 4. メモリ：スタックとヒープ

ざっくり二層です。

```text
┌───────────── スレッドごと ─────────────┐
│ スタック (stack)                                                 │
│  ・メソッド呼び出しの「枠」（フレーム）                          │
│  ・ローカル変数、引数、戻り先                                    │
│  ・スコープを抜けると枠が消える                                  │
└─────────────────────────────────┘

┌───────────── プロセスで共有 ───────────┐
│ ヒープ (heap)                                                  │
│  ・new したオブジェクトの本体                                  │
│  ・配列の実体                                                  │
│  ・GC が不要になったものを回収                                 │
└────────────────────────────────┘
```

```java
void sample() {
    int count = 3;                 // スタック上のローカル変数
    Book book = new Book("Java");  // book（参照）はスタック、Book 本体はヒープ
}
```

- **プリミティブ**（`int` など）のローカル変数はスタックに乗る
- **オブジェクト**はヒープ。変数が持っているのは参照（住所）
- メソッドを呼ぶたびにスタックフレームが増え、return すると減る
- 再帰が深すぎると `StackOverflowError`（04 章の Error）
- オブジェクトを作りすぎ／捨て損ねると `OutOfMemoryError`（ヒープ不足）

クラスのメタ情報（メソッドの形など）は、現代の JVM では **Metaspace** と呼ばれる領域に近い場所へ置かれます。最初は「ヒープ＝オブジェクト、スタック＝呼び出しとローカル」で十分です。

### 5. スコープ（変数の見える範囲と寿命）

スコープは「その名前が使える範囲」であり、寿命は「その値が残る期間」です。Java ではブロック `{ }` が基本単位です。

| 種類 | 宣言場所 | 見える範囲 | 寿命 |
|------|----------|------------|------|
| ローカル変数 | メソッド／ブロック内 | そのブロックの終わりまで | スタックフレームとともに消える |
| 引数 | メソッド引数 | メソッド全体 | 呼び出しが終わるまで |
| インスタンス変数 | フィールド | インスタンスのメソッドから | オブジェクトが GC されるまで |
| クラス変数 | `static` フィールド | クラス全体（全インスタンスで共有） | クラスがアンロードされるまで |

```java
public class ScopeDemo {
    static int classCount = 0;   // クラス変数（共有）
    int id;                      // インスタンス変数（オブジェクトごと）

    void run() {
        int local = 1;           // ローカル
        if (local > 0) {
            int inner = 2;       // if ブロックの中だけ
            System.out.println(inner);
        }
        // System.out.println(inner); // コンパイルエラー：スコープ外
    }
}
```

実務で効くこと:

- ループ変数 `i` は `for` の `()` 内で宣言すると、ループの外から見えない
- 同じメソッド内でも、ブロックを出た変数は使えない（意図しない使い回しを防ぐ）
- `static` は「全インスタンスで共有」なので、カウンタ以外の可変状態には慎重に

### 6. GC（ガベージコレクション）

ヒープ上のオブジェクトは、参照がどこからも辿れなくなると **ゴミ** とみなされ、GC が回収します。C 言語のように `free` を自分で書く必要は原則ありません。

ただし:

- コレクションやキャッシュに参照が残り続けると、回収されない（メモリリークに見える）
- GC は「いつ走るか」をアプリが完全には制御しない
- ファイルや DB 接続は GC 待ちにせず、`try-with-resources` で閉じる（05 章）

### 7. キャッシュ（JIT・CPU・アプリ）

「キャッシュ」は層が違うと意味が変わります。混同しやすいので分けます。

| 層 | 何を覚えているか | 開発者が触るか |
|----|------------------|----------------|
| **CPU キャッシュ** | 最近使ったメモリのコピー（L1/L2/L3）。近いデータを繰り返し使うと速い | 直接は触らない。配列の連続アクセスが有利、など背景知識 |
| **JIT コードキャッシュ** | よく実行されたバイトコードをマシン語にした結果 | JVM 内部。ウォームアップ後に速くなる現象の正体の一つ |
| **アプリのキャッシュ** | 計算結果や DB の行を自分で Map 等に保持 | 設計対象。上限と期限を決めないとヒープを食う |

配列が List より速いことがある、ループを何回か回すと速くなる、というのは、CPU キャッシュや JIT の影響です。  
最初から「キャッシュで速くする」より、正しいコード → 計測 → 必要なら最適化、の順です（09 章の YAGNI / 計測）。

### 8. クラスローダの入口

JVM は必要なクラスを、実行中に **クラスローダ** が読みます。

```text
java HelloWorld
  → HelloWorld.class を探す（クラスパス）
    → 依存クラスも順にロード
      → main を実行
```

クラスパスが違うと `ClassNotFoundException` / `NoClassDefFoundError` になります。  
パッケージ付きサンプルで `-cp` を指定するのは、このためです。
