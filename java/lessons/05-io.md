## この章の目標

- テキストファイルの読み書きができる
- `try-with-resources` でリソースリークを防げる
- 文字コードとパスの基本を意識できる
- `System.out.println` と Logger の使い分けを説明できる

## なぜ大事か

アプリはメモリの中だけで完結しません。設定・ログ・ユーザーデータはファイルやネットワークに出ます。  
リソースを閉じ忘れると、本番で「ファイルが開けない」「ディスクが枯渇する」といった障害になります。

また、学習中は `System.out.println` で十分ですが、本番では **いつ・どの深刻度で・どこに残すか** を制御できるログ基盤が必要です。障害調査の一次情報源になるのがログです。

## 学習ポイント

### 1. パスとファイル

```java
Path path = Path.of("data", "notes.txt");
```

`java.nio.file` を優先して使います（古い `File` より現代的）。

### 2. 読み込み

```java
List<String> lines = Files.readAllLines(path, StandardCharsets.UTF_8);
```

小さなファイルなら一括読み込みで十分です。巨大ファイルはストリームで行単位に処理します。

### 3. 書き込み

```java
Files.writeString(path, "hello\n", StandardCharsets.UTF_8);
```

### 4. try-with-resources

`AutoCloseable` を自動で閉じます。

```java
try (BufferedReader reader = Files.newBufferedReader(path)) {
    String line;
    while ((line = reader.readLine()) != null) {
        System.out.println(line);
    }
}
```

`finally` で `close()` を書くより安全で短いです。

### 5. コンソール出力と Logger

#### `System.out.println` が向く場面

この教材のサンプルでも多用しています。次のような用途では問題ありません。

- 学習・実験・一時的な確認
- CLI の **ユーザー向け表示**（プロンプト、一覧、ヘルプ）
- ごく短いデモプログラム

```java
System.out.println("合計: " + total); // ユーザーへの結果表示としては妥当
```

#### 本番アプリで println だけだと困る理由

| 課題 | 内容 |
|------|------|
| レベルがない | 調査用の詳細と、致命的エラーが同じ流し方になる |
| 出力先が固定 | コンソール以外（ファイル、集約基盤）へ切り替えにくい |
| 制御しにくい | 本番だけ黙らせる、特定パッケージだけ詳しく、がやりにくい |
| 構造化されにくい | 時刻・スレッド・ロガー名・例外スタックの付け方がバラバラ |
| 性能・ノイズ | ホットパスでの大量 println は Contended になりやすく、ログ洪水にもつながる |

#### Logger とは

**ロガー**は、「メッセージ＋深刻度（レベル）」を、設定に従って出力する仕組みです。  
コード側は「何が起きたか」を書き、**どこに・どの詳細さで出すか** は設定側に寄せます。

この教材では依存追加なしで学べる **`java.util.logging`（JUL）** を使います。実務では **SLF4J + Logback**（や Log4j2）が非常によく使われます。書き方の感覚は共通です。

```java
import java.util.logging.Level;
import java.util.logging.Logger;

public class OrderService {
    private static final Logger logger = Logger.getLogger(OrderService.class.getName());

    public void place(Order order) {
        logger.info("注文を受け付けました: id=" + order.getId());
        try {
            // ...
        } catch (RuntimeException e) {
            logger.log(Level.SEVERE, "注文処理に失敗しました: id=" + order.getId(), e);
            throw e;
        }
    }
}
```

#### ログレベル（JUL）

| レベル | 目安 |
|--------|------|
| `SEVERE` | 処理継続が難しい致命的な失敗 |
| `WARNING` | 異常だが回避・リトライできるかもしれない |
| `INFO` | 運用上意味のある出来事（起動、受付、完了） |
| `FINE` / `FINER` / `FINEST` | 開発・詳細調査用（本番では通常オフ） |

SLF4J / Logback では `error` / `warn` / `info` / `debug` / `trace` という名前が一般的です。対応関係のイメージは `SEVERE≈error`, `WARNING≈warn`, `INFO≈info`, `FINE≈debug` です。

#### println と Logger の使い分け

| 用途 | 推奨 |
|------|------|
| CLI でユーザーに見せる文言 | `System.out` / `System.err`（または専用 UI 層） |
| 障害調査・監査・処理トレース | Logger |
| 「今変数の中身は？」の一時確認 | 学習中は println でも可。残すなら `FINE` やデバッガへ |
| 例外の記録 | `logger.log(Level.SEVERE, msg, exception)` のように **cause 付き** |

ポイント: **ユーザー向けメッセージ** と **運用向けログ** を混ぜない。  
CLI なら「画面に出した内容」と「ログに残す内容」は別物として考えます（10 章のミニアプリでも、UI は println、将来の拡張では service 層に logger、が自然です）。

#### 書いてはいけないもの

- パスワード、トークン、個人情報の生値
- 巨大すぎるペイロード全文（必要なら ID や件数に要約）
- 例外の握りつぶし（log して終わり、呼び出し側に伝えない）の常態化

#### 実務でよく使うスタック（参考）

```text
アプリコード  →  SLF4J API（ログの書き口）
                  ↓
              Logback / Log4j2（実装・出力先・フォーマット）
```

JUL のままでも動きますが、ライブラリごとにログ実装が割れるのを避けるため、アプリでは SLF4J 経由に揃えることが多いです。ビルドツール（07 章）を導入したあとに依存追加するとスムーズです。
