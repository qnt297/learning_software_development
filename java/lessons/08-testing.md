## この章の目標

- 「テスト可能な単位」でコードを分割する感覚を得る
- アサーション（期待値と実際の値の比較）で振る舞いを固定する
- JUnit の位置づけと、カバレッジ・静的解析（SpotBugs 等）の役割を説明できる
- テストファーストの入口（先に失敗するテストを書く）を体験する

## なぜ大事か

手動確認だけに頼ると、変更のたびに回帰バグが増えます。  
自動テストは、未来の自分とチームへの「仕様の契約書」です。  
ただしテストだけでは見つからない欠陥（リソースリーク、典型バグパターン、未実行の分岐）もあるため、**カバレッジ** や **静的解析** と組み合わせるのが現代的な品質づくりです。

## 学習ポイント

### 1. 何をテストするか

- **ドメインロジック**（計算・判定・状態遷移）を優先
- UI の見た目や、単なる getter は優先度を下げる

### 2. 良いテストの形（AAA）

1. **Arrange**: 前提データを用意
2. **Act**: 対象メソッドを実行
3. **Assert**: 結果を検証

### 3. この教材での簡易テストと JUnit

本番では **JUnit 5（Jupiter）** を使います。ここでは依存なしで学べるよう、小さな `Assert` ユーティリティと `*Test` クラスを自前実装しています。

```java
Assert.assertEquals(3, calculator.add(1, 2));
```

JUnit に移行するイメージ:

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

class PriceCalculatorTest {
    @Test
    void withTax_addsTenPercent() {
        PriceCalculator calculator = new PriceCalculator();
        assertEquals(1100, calculator.withTax(1000, 0.1));
    }
}
```

`@Test` もアノテーションです。意味や自作の入口は [02. オブジェクト指向（アノテーション）](02-oop.md) を参照してください。

| 自前 | JUnit 5 |
|------|---------|
| 手書きランナー | ビルドツールが検出・実行 |
| 自作 `Assert` | `Assertions` / AssertJ など |
| 命名ルールのみ | `@Test`, `@BeforeEach`, `@ParameterizedTest` |

関連エコシステム（名前だけ押さえる）:

- **Mockito** … 依存オブジェクトのモック
- **AssertJ** … 流暢なアサーション
- **Testcontainers** … 実 DB などをコンテナで統合テスト

### 4. コードカバレッジ

カバレッジは「テスト実行時に、どの行／分岐が通ったか」を測る指標です。

| 種類 | 意味 |
|------|------|
| 行カバレッジ | 何行が実行されたか |
| 分岐カバレッジ | if / switch の両枝などが通ったか |
| メソッドカバレッジ | メソッドが呼ばれたか |

代表ツール:

- **JaCoCo**（Java で最も一般的）
- IntelliJ のカバレッジ実行
- Maven / Gradle プラグイン経由でレポート生成

#### 使い方のコツ

- **100% を盲目的な目標にしない**。getter を全部通しても品質は保証されない
- 「重要な業務分岐が赤い（未実行）」を優先して埋める
- カバレッジは **不足の発見** には効くが、**テストの質（意味のある検証か）** は保証しない
- CI でしきい値（例: 新規コードの分岐カバレッジ ○%）を設けるチームも多い

### 5. 静的解析・バグパターン検出（SpotBugs など）

テストが「実行して確かめる」のに対し、静的解析は **実行前にソース／バイトコードを検査** します。

| ツール | 役割のイメージ |
|--------|----------------|
| **SpotBugs** | 典型的なバグパターン検出（NPE の可能性、リソース未クローズ、まずい equals など） |
| **FindBugs** | SpotBugs の前身（後継として SpotBugs を使う） |
| **Error Prone** | コンパイラプラグインとして危険な API 使用などを検出 |
| **Checkstyle** / **PMD** | スタイル・複雑度・一部の悪い癖 |
| **Null 解析**（SpotBugs の注釈、IDE、Checker Framework 等） | null 安全性 |

SpotBugs が見つける例のイメージ:

- 例外を握りつぶしている
- `equals` をオーバーライドして `hashCode` を忘れている
- ストリーム／接続を閉じていない可能性
- 無意味な条件、デッドストア（代入して未使用）

#### テストとの役割分担

```text
ユニットテスト     … 「仕様どおり動くか」を実行で固定
カバレッジ         … 「テストが触っていない穴」を可視化
静的解析(SpotBugs) … 「実行しなくても怪しいパターン」を検出
```

どれか一つでは足りません。テストが緑でも SpotBugs が赤、あるいはカバレッジが低い、ということが普通に起きます。

#### 導入の現実的な進め方

1. まず JUnit でドメインのテストを書く
2. JaCoCo で「重要な未カバー」を見る
3. SpotBugs（や IDE インスペクション）を CI に載せ、新規警告から潰す
4. 一気に全警告ゼロを目指すより、深刻度の高いものから

### 6. テストしやすい設計

- 副作用（標準出力・ファイル）をロジックから分離する
- 静的メソッドやシングルトンを乱用しない
- 入力を引数、出力を戻り値にする

静的解析やカバレッジを回しやすくするのも、結局はこの設計に依存します。
